# 2026-09-11

Phase 3 — Declaration (DC01–DC03) + the Terms Acceptance gap left open since Foundations.

## 1. Two things that look alike but aren't

The first thing worth writing down, because it caused a round of confusion mid-session: this module covers **two separate consent-ish features**, and the schema deliberately keeps them in different tables.

| | What the client is saying | Where | Table |
| --- | --- | --- | --- |
| **Terms and Conditions** | "I agree to the terms of using PsyCare 2.0" | Blocking pop-up on first portal use | `terms_acceptances` |
| **Client Information Declaration** | *"Saya mengaku bahawa segala maklumat yang diberikan adalah BENAR…"* | Pengesahan / Confirmation tab | `declarations` |

Both were previously faked in one localStorage file (`resources/js/lib/psycare-declaration.ts`). Both are now real, and still separate.

## 2. Decisions taken before building

- **Who verifies a declaration?** DC03 names both Admin and Counsellor, but only Admin has a Client Information page. Decided: **both roles**, with the counsellor reaching a client's declaration from the appointment they're already reviewing rather than inventing a new page for them.
- **What is the client declaring, and how often?** The schema allows a declaration to be standalone or attached to an appointment. Decided: **profile-level, submitted once** — they declare that their Client Information Form is true. `appointment_id` stays null, and the booking form deliberately did *not* gain a declaration checkbox.

## 3. What was built

**Backend**
- `App\Services\DeclarationService` — the DC01–DC03 transitions in one place: submit (EF1: tick the box first), verify (EF1: can't verify what was never submitted; EF2: already verified), request-correction (note required, since that note is what the client has to act on). Every outcome writes a `declaration_verification_events` row, so the history survives even though the declaration row itself is updated in place.
- `DeclarationController` (client submit), `Admin\DeclarationController` and `Counsellor\DeclarationController` (verify / request correction). The two verifier controllers are separate but share the service, so the roles can't drift apart — same pattern as the Phase 2 slot controllers.
- `App\Services\TermsAcceptanceService` + `TermsAcceptanceController`. Acceptance is recorded per client **per version**, so bumping the version re-prompts everyone while their earlier acceptance stays on record as proof of what they agreed to at the time.
- `config/psycare.php` holds the terms version and the declaration wording. The wording is **copied onto each declaration row at submission time** — editing the config later never rewrites what past clients actually agreed to.
- `HandleInertiaRequests` now shares a `termsAcceptance` prop. It's null for anyone who isn't a client with a profile, which is how the admin and counsellor portals never see the pop-up.

**Frontend**
- The blocking pop-up in `psycare/Layout.tsx` is server-driven now. Accepting posts for real; the modal also closes optimistically so a client isn't left staring at a blocking overlay while the refreshed props travel back.
- The Pengesahan tab in `ClientProfileForm.tsx` submits for real and shows the outcome back to the client — including the correction note, with resubmission allowed after a correction and locked once verified.
- `admin/client-information.tsx`'s Pengesahan tab and the counsellor's appointment review modal both verify or request corrections, with an explicit empty state when a client hasn't declared yet.
- Deleted `psycare-declaration.ts` and the prototype "Status Deklarasi" toggle that let a client flip their own declaration to Submitted without actually submitting it. DC02 AF2 itself describes that toggle as a *prototype control*, so removing it was the honest reading.

## 4. Bug found while testing

`admin/client-information.tsx` called `record.status.toUpperCase()`, but `ClientInformationController::present()` never returned a `status` key — so the **entire admin Client Information page blanked out whenever any record existed**. It had gone unnoticed because the Pest test only asserted Inertia props and the Phase 2 browser run never opened that page.

`clients` has no status column (a Phase 1 finding), so the value now reports the linked login account's state instead, the UI guards the field, and a test asserts the key is present.

## 5. Also fixed: stale Vite build

Two Phase 2 tests were failing before I touched anything — `counsellor/slots.tsx` wasn't in `public/build/manifest.json`, which was dated Aug 16, before that page existed. Not a code problem; `npm run build` cleared it. Worth remembering that a stale manifest surfaces as a confusing 500 rather than a missing-asset error.
