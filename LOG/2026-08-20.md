## 2. Bug fix — counsellor-stage status showed "Approved" before any review happened

Reported: opening a brand-new `pending` appointment's review modal showed **Counsellor Stage: APPROVED** — wrong, since admin hadn't even reviewed it yet.

Root cause: both portals' "Counsellor Stage" label only checked for `needs_review`/`counsellor_reviewing` as PENDING and treated *everything else* (including plain `pending`) as APPROVED. Fixed in both `admin/appointments.tsx` and `counsellor/appointments.tsx` with one shared rule: PENDING while status is `pending`/`needs_review`/`counsellor_reviewing`, APPROVED only once it's `approved` or later (`on_going`, `complete(d)`, `follow_up`, `closed`).

## 5. Slot Manager — split into two real pages, not one shared component

Caught mid-redesign: Admin's page and the Counsellor's page had been merged into one component branching on role (`isScoped` conditionals). Explicitly told not to do that — admin manages *every* counsellor's slots, counsellor manages only their own, and the two are different enough jobs to deserve different pages, matching the existing `Admin\AppointmentController`/`Counsellor\AppointmentController` split.

- New `App\Services\SlotScheduleService` — the actual persistence/overlap-checking logic, shared so the two roles' behaviour can't drift apart.
- `Admin\SlotController` trimmed to admin-only (full access, no scoping code).
- New `Counsellor\SlotController` — resolves the logged-in counsellor, force-assigns new slots to them, rejects deleting anyone else's slot, 403s if there's no linked `Counsellor` record.
- New `resources/js/pages/counsellor/slots.tsx` — no counsellor picker anywhere, since there's nothing to pick. `admin/slots.tsx` keeps a counsellor picker on every action plus a "view calendar for" filter across all counsellors (added since an unfiltered mixed-counsellor calendar would have been exactly the "overwhelming" problem again, just for admins instead of counsellors).
- Removed the legacy **Counsellor Timetable** page (`admin/counsellor-timetable.tsx`) — a pre-Phase-2 mock duplicate of Slot Manager with its own counsellor picker, saved to `localStorage`, never wired to the database. `/admin/counsellor-timetable` now redirects to `/admin/slots`; the admin sidebar's dead link was replaced with a working "Slot Manager" link (the admin nav had never actually linked to the real page at all — an oversight from the first Phase 2 pass).

## 6. Performance fix — slot save timing out on large batches

Reported: saving many slots at once eventually hit `Maximum execution time of 30 seconds exceeded`.

First pass fixed the obvious thing (an `Eloquent::create()` loop, one row at a time) but that turned out not to be the dominant cost. Instrumenting the actual query log found the real cause: **Laravel's `exists:table,column` validation rule on a `field.*.x` wildcard array runs one query per array item, not one batched query.** With a routine 360-slot bulk-generate result, `new_slots.*.counsellor_id`/`location_id`'s `exists` rules fired **720 individual existence-check queries against Supabase before a single slot was even saved** — that's what was actually timing out.

Fixed in `SlotScheduleService`:
- Validation now only checks format (`uuid`), no DB hit per item; referential integrity moved into the service as two bulk `whereIn` checks (one query total for every counsellor id referenced, one for every location id) — O(1) queries instead of O(n).
- Slot + session-type rows built in PHP, written via `insert()` in chunks of 500 — one query per chunk instead of one per row.
- `presentUpcoming()` now uses `withCount('appointments')` instead of a per-slot `->count()` (was an N+1 hit on every page load, not just save).
- The EF2 overlap check fetches every potentially-conflicting slot in one query and compares in memory, instead of one query per counsellor/date pair.
- Along the way, refixed a bug reintroduced during the rewrite: `whereBetween('slot_date', [...])` against raw date strings breaks under SQLite (test env) because the column can come back with a time suffix — switched back to `whereDate()`, the same fix already applied once earlier in the week for the same underlying issue.

Verified with a regression test: 360 slots (90 days × 4 slots, a realistic AS05 result) saved in one request, asserted total query count stays under 20 (was 720+), completes in ~0.26s.
